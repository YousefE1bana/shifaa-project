# Autonomous Engineering Delivery Policy

Candidate policy `SHIFAA-AUTONOMOUS-DELIVERY/1.0.0`. Governing scope is
prospective Graduation MVP engineering. The Product Owner's direct directive
“SHIFAA — Product Owner Directive: Autonomous Engineering Delivery” authorizes
preparation and implementation. Activation requires the exact ratification
and integration below.

## Standing delegation

The root owns bounded, reversible technical and design choices, implementation,
testing, reviews, and repair within approved requirements. It drives SpecKit
through evidence-based checkpoints, manages feature branches and PRs, squash
merges eligible PRs under actual account permissions, verifies remote main,
reconciles the primary checkout, finalizes evidence, and closes completed
Issues after their closure conditions pass. It then takes the next eligible
task. Preserve published branch history with a normal merge from main when
synchronizing an existing PR. A rebase is permitted on unpublished isolated
work with a clean worktree and preserved evidence.

Read the approved roadmap row, requirements, contract versions, and applicable
authority. Record the actual repository, worktree, branch/HEAD and
`.specify/feature.json` before invoking a stage. At each checkpoint record the
exact input revision or hashes, mapped requirement IDs, prerequisites, applicable
gates, evidence and result in the owning artifact or existing ledger. The root
accepts the exact technical Plan after architecture completeness and proceeds
to Tasks under standing delegation. Perform analysis, baseline integration and
Issue handoff once their own prerequisites pass. Use the canonical Issue mapping
and existing Issues. In Issue-scoped mode, use the assigned task and its
incomplete authorized dependency closure. An absent/stale pointer, an unresolved
blocking prerequisite or a reserved decision stops the affected stage.

The checked-in SpecKit workflow uses individual `approve` / `reject` verdicts
with empty defaults. The root supplies only the reached checkpoint's verdict
after inspecting evidence and ownership. Never prefill future verdicts. A CLI
verdict expresses a recorded decision. A command's completion, free-form input
or a reviewer label cannot supply that decision. Individual official SpecKit
commands follow the same gates when a CLI integration cannot run the complete
workflow safely. Before Issue publication, verify the published exact task
baseline, its required integration, clean HEAD/upstream and the feature-qualified
dependency mapping. Finalization follows verified integration and the
[Feature Artifact Finalization Gate](SHIFAA-Feature-Artifact-Finalization-Gate.md).

## Verification by impact

Use the highest applicable row and combine affected obligations. Every PR requires
review, resolved blocking threads, all six required CI contexts and fresh metadata
against the actual head, a verified integration base, and repository permissions.
Keep executed PASS, failures, omissions and unexecuted checks distinguishable.

| Impact                                                  | Minimum evidence beyond repository gates                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Documentation, static evidence, routine dependencies    | Verify scope, links, syntax, hashes and preservation as applicable. For dependencies use pinned frozen resolution, unfiltered advisory reporting, and affected build, type and regression checks. Reassess runtime or security impact when affected.                                                                                                       |
| Application behavior or UI                              | Exercise affected contracts, normal and degraded flows, regression and boundary conditions. For affected UI include Arabic RTL, English LTR and accessibility automation. Attach actual human or native evidence where the approved feature or milestone requires it.                                                                                      |
| Security, authorization, database or migrations         | Review changed trust boundaries and callers. Run applicable non-owner and cross-tenant negatives, current authority/independence, forced RLS, audit/outbox/idempotency, rollback, race and recovery checks on isolated resources. Prove fresh and upgrade migration paths and native behavior where contracted. Preserve independent review when required. |
| Regulated, real data, live infrastructure or production | Obtain the named statutory, clinical, legal/privacy, facility, vendor, or production decision and release evidence before the affected activity. Run the applicable engineering and independent specialist checks.                                                                                                                                         |

Classify semantic impact in the PR. Routine maintenance and security fixes
within accepted trust boundaries use technical verification and delegated
integration. A change to fundamental governance/architecture, material scope,
trust/authorization boundaries or critical safety protections requires the
applicable reserved decision. Production, lawful PHI use, professional signatures
and irreversible retained-resource operations require their own real authority.
No review can be fabricated. Preserve legally required separation of duties,
independent review and branch protection. When a mandatory check is unavailable,
record its exact scope and the affected capability. Keep the affected merge or
release blocked unless the governing authority permits an attributable bounded
disposition and repository protection still passes.

## Human evidence and progress

Request evidence directly from the responsible teammate through an authorized
channel. Give the exact revision/build, setup and test inputs, steps, expected
outcome, evidence to capture and how to report actual failures. Ask for the
applicable Arabic/English, device, native assistive-technology, product or
specialist checks. Record the actual person, time, tested scope and result.
Continue independent work while waiting and resume the affected work when
valid evidence arrives. A missing result is pending. Automated checks and
screenshots supply only the coverage they actually exercise.

Use the [delivery dashboard](SHIFAA-Engineering-Delivery-Dashboard.md) as a
concise view over the roadmap, task ledgers and GitHub. Refresh it during active
delivery. Canonical sources carry the actual status. Parallelize only eligible,
disjoint work within supported agent limits. Serialize shared Docker/database
harness operations until isolation is proven. Preserve synthetic-only admission,
the Core API boundary, existing `OPEN-*` gates, and `not_fully_checked`.
Use the [safe verification guide](../testing/SHIFAA-Safe-Verification.md).
