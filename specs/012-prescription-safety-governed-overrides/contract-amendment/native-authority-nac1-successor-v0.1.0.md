## 3. Closed access-currentness predicate

Before protected disclosure or effect, server verifies signature/key/issuer/audience, subject, session ID, required AAL2 and F007 qualifying TOTP-event timestamp. Bind the verified subject/session to current F007 person mapping, action, facility, purpose, case/lane/assignment where applicable. Never trust request-body authority, mutable user metadata, client time or refreshed JWT `iat` as factor evidence. Recheck token expiry and qualifying event freshness after lock waits; retain F007 whole-second inclusive five-minute freshness, reject future evidence. This port does not independently invent JWT/factor rules.

## 4. Merged lock graph and serialization

One PostgreSQL connection, one READ COMMITTED guarded transaction: **A-DB admission → idempotency scope → user SHARE → current session SHARE → producer generations/local authority/domain ranks** from the source successor. No user/session lock upgrade, SKIP LOCKED admission, remote call or network operation inside the F012 guarded transaction. Fresh statements and clock checks follow waits. Hold both native locks through domain/audit/outbox/obligation/P2/P3/idempotency commit or rollback.

## 5. Exact internal interface and least-privilege delta

Proposed `NativeAuthorityGuard.retain(tx, verifiedContext)` consumes the **same** already-active repository transaction/connection. Verified context contains server-derived subject/session/person, verified AAL/TOTP event/token expiry, current action/facility/purpose/case binding and deployment receipt. Result is success or a closed denial/unavailable classification; no Auth row, factor secret, AMR history, credential or unrelated identity is returned. S4 invokes it as the independently assigned reviewer, never as the prescriber. It is not a thirteenth public operation.

The current boolean helper is not sufficient, and its observed `postgres`/BYPASSRLS definer ownership must **not** be copied into the new port. Observed native `auth.users` and `auth.sessions` have enabled RLS, no force and zero policies; the normal API role has no SELECT and no BYPASSRLS. Therefore a non-owner implementation cannot merely add SELECT FOR SHARE and assume it works.

The exact proposed permission delta is a dedicated **internal NOLOGIN, NOSUPERUSER, NOBYPASSRLS, non-table-owner function executor**, distinct from the F011 protected executor and from every business/reviewer role. Its creation/ownership/policies require this successor's exact governed acceptance; **no such role or grant is installed by this document**. Do not reuse the F011 protected executor, use native table ownership, or give the normal API role Auth-table access as a shortcut.

Minimum future privilege contract:

- Fixed-search-path SECURITY DEFINER helper in `platform`, owned only by that internal executor; `PUBLIC`, anon, authenticated and worker EXECUTE revoked; only the existing Core API role may execute the bound guard. No membership/SET ROLE capability from API/worker to the executor; no dynamic SQL or arbitrary table/column parameters.
- Exact native columns: users `id,instance_id,banned_until,deleted_at`; sessions `id,user_id,aal,not_after`. PostgreSQL locking SELECT additionally needs UPDATE privilege on at least one column: constrain it to `id`, with bound-row SELECT/UPDATE USING policies and `WITH CHECK (false)` preventing actual modification. No INSERT/DELETE, credential, token, factor or unrestricted row grants. [PostgreSQL SELECT privileges](https://www.postgresql.org/docs/17/sql-select.html), [policy semantics](https://www.postgresql.org/docs/17/sql-createpolicy.html).
- The executor is subject to RLS. Native user rows are limited to the verified subject; session rows to the exact current server-bound session and matching subject. Identity mapping access is only `identity.people(id,user_id)` for the current actor, under enabled/forced RLS and a separate exact executor policy. Validate current actor/person/subject binding and session context before setting any internal bound-subject context used by native policies. Empty, malformed or mismatched context denies. Normal online clients cannot set database context or call SQL directly.
- API verifies signed native context; database guard and independent F012 forced-RLS policies recheck the bound current actor/action/facility/purpose/case/assignment and evidence predicates. Neither layer substitutes for the other. A forged/missing GUC, cross-subject/session/case substitution, or direct executor invocation must fail in later non-owner tests. Native Auth retains its existing owner/writer semantics; this candidate does not globally FORCE native tables and break the vendor.

This is a prepared physical privilege design, not proof of an installed policy or permission. The exact function/grant/RLS SQL and its generated-contract parity must implement these clauses after acceptance and separate implementation authorization. Failure to realize this bound non-owner design blocks the port; a privileged boolean fallback is forbidden.

## 6. Competing paths and linearization

```text
F012 guarded action (future implementation):
  verify signed JWT/context outside transaction; resolve no remote dependencies under locks
  BEGIN READ COMMITTED on the owning repository connection
  take A-DB admission and original idempotency scope in accepted order
  validate deployment receipt; retain bound user SHARE then current-session SHARE
  re-evaluate token/TOTP/NotAfter using fresh clock after waits
  retain local recovery, care/facility/designation/assignment and producer protections
  validate current S4/current evidence, aggregate CAS and independent evidence digest
  recheck deadlines; perform the guarded conditional effect (logical action ordering)
  write P2 lineage/P3 statement when applicable, obligation, audit, outbox, canonical receipt
  recheck deadlines/commit obligations; COMMIT or ROLLBACK everything

Native invalidation (existing native writer, not an F012 HTTP sub-call):
  BEGIN native transaction; run source-defined ban/logout/downgrade/password SQL
  conflicting user/session write waits for retained SHARE, or wins before guard admission
  if inverse order forms a deadlock, PostgreSQL aborts one entire transaction
  COMMIT native effect; independent HTTP response/local F007 audit may follow
```

Revocation-first means the guard's fresh locked read denies the invalid current state. Action-first means native invalidating SQL cannot commit past retained protection until the guarded transaction ends; it does not promise HTTP-request-arrival priority or authorize another action after revocation. Logout HTTP start is not its linearization point. Missing/deleted rows never produce optimistic admission. Locks serialize writers, not time: recheck deadlines before effect/finalization and abort expired work, without claiming physical WAL commit before wall-clock expiry.

Deadlock, timeout, crash or failed guard rolls back all required F012 effects; previous committed drafts and signed history remain intact. Lost response after possible commit is **unknown**, reconciled by original key under fresh current authority. Sensitive unauthorized replay reveals no earlier response; authorized replay adds no signature, successor, statement or obligation. Receipt-finalization/audit/outbox failure cannot leave partial success. Native Auth timeout likewise does not prove native rollback.

## 7. Deployment admission and unsupported writers

Admission binds the immutable image/source, this effective policy/carrier hash, actual container/start, authoritative schema/helper version, enabled writer inventory and current A-DB epoch. Normal user requests cannot repair or self-admit it. Configuration, image/digest/source, hooks/providers/admin paths, session/MFA policy, schema/policies/helper, writer topology or reload/startup identity changes require disabling/draining sensitive F012 effects, non-destructive compatibility verification and explicit operator re-admission with a new receipt/epoch. Missing or stale evidence fails closed.

This is an isolated trusted-operator deployment contract, not a claim that an A-DB row locks Docker, filesystem edits, a remote process or arbitrary DBA actions. Carrier is read-only inside Auth; host/operator changes remain controlled maintenance. Current arbitrary direct SQL factor-only mutation, unknown hook/writer, or unmanaged configuration change is **not admitted**. Native built-in direct/admin paths are admitted only with the inspected source-defined conflicting effects. No shadow ledger can turn an unrepresented external invalidation into valid authority.

The original Auth container is retained stopped/disconnected for rollback. Starting it restores the previous unpinned identity and therefore withdraws NAC-1 admission. A CLI stack recreation also requires fresh readback; stock CLI omission of disabled hooks cannot silently inherit this receipt. No second Supabase stack is required.
