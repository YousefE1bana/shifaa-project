## 3. Protocol disposition and minimum missing native contract

Retain **A — native-authority validation/protection inside the same guarded PostgreSQL transaction** as the sole conditional target, not an accepted protocol. No alternative ledger or repeated boolean check is substituted.

Direct repository findings:

- [SQL helper](../../../supabase/migrations/20260825000700_identity_continuity_sessions_mfa_recovery.sql), lines 224–261: `platform.auth_session_is_current` is a fixed-search-path, boolean-only `SECURITY DEFINER` existence/AAL/NotAfter check. No retained row lock or complete user/factor/refresh-family validity contract is supplied.
- [Repository](../../../services/api/src/adapters/postgres/identity-repository.ts), lines 48–64: `withRawTransaction` reuses the active transaction when present, otherwise starts one. It is incorrect to claim it always uses a separate transaction. Reuse supplies a connection boundary, not native authority protection.
- [Continuity adapter](../../../services/api/src/adapters/postgres/identity-continuity-service.ts), lines 49–108: native boolean validation and restriction lookup use that repository. [Service](../../../services/api/src/modules/identity-continuity/service.ts), lines 177–206: Auth HTTP logout occurs before later local audit. HTTP invocation order and local audit order are not native SQL serialization proof.

Conditional linearization argument: only after a version-bound complete native predicate/writer contract exists may a permissioned internal helper lock every relevant native/local authority resource in a proven compatible total order on the retained F012 connection. Revocation committed first must cause a fresh post-wait denial; guard acquired first may retain the required conflicting resources through the F012 atomic domain/audit/outbox/idempotency effect and commit. HTTP request start does not choose the winner. Time-based predicates require real-time post-wait and guarded-effect checks; no row lock freezes time or guarantees physical commit before wall-clock expiry.

The inspected candidate suggests session UPDATE/DELETE conflicts are useful, but **does not establish** complete user/factor/refresh/recovery predicates, writer admission, absent-row behavior or a total lock graph compatible with A-DB/F007/F011. Candidate `CheckValidity` uses strict `now.After(...)`; the existing SHIFAA NotAfter helper denies at equality (`not_after > clock_timestamp()`). These must not be silently conflated into a new expiry policy. Native read paths also contain `FOR UPDATE SKIP LOCKED`; a proposed reader lock cannot be assumed transparent to native refresh/session behavior.

An accepted successor would have to extend the existing F007 boolean-only boundary explicitly, with no ordinary application access to Auth tables, no service-role bypass, a minimal validation result, current identity/AAL/recovery predicates, permissioned retained connection protection, current-context forced RLS, replay denial after authority loss, and exact lock/deadlock/uncertain-commit recovery. Those are contract obligations, not claims that a helper is installed. S4 remains case-bound validation only; P1/P2/P3 and exactly twelve public operations remain unchanged.

No versioned F007/F012 successor is created on this evidence. Missing source identity and native writer semantics are design facts, not future race tests. Source-dependent reviewer decisions/simulated signing remain fail-closed; this document does not claim an implemented F012 runtime control.
