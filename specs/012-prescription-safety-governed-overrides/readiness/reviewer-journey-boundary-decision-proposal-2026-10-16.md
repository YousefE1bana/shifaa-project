## 4. Designation, case and assignment contract

**Roster:** version/digest and deployment identity; synthetic person/account mapping; lane designation; originating facility and explicit case or bounded scope; validity interval; revision and revocation state. These are proposed engineering metadata, never professional licenses. Provision and revoke through an explicitly reviewed deployment configuration artifact under the existing authorized engineering change process, outside the F012 online user-operation inventory. There is no runtime roster-management API or admin UI. If online roster administration later becomes necessary, this twelve-operation proof does not cover it and requires a new boundary decision.

**Case/evidence binding:** request/issue/prescription/item revisions and digests, relevant allergy and medication-history snapshot identities/completeness, mechanism-fixture provenance, lane, roster/policy revisions, expiry and decision/assignment revisions. Research provenance belongs to the separate nonclinical display, not an override-authorizing case. Never use an old signature/digest as proof of current authority. Exact hashes, identifier types and storage constraints require Plan design. Changing medication/history/content invalidates any affected current authorization; never silently rebind an old decision.

Separate the immutable review-evidence fingerprint from mutable aggregate CAS versions. Claiming a different lane or recording its decision changes the aggregate version but does not itself change the clinical/mechanism evidence fingerprint or erase the other lane's decision. Each mutation must use the latest aggregate/own-assignment revision; decision usability requires its unchanged evidence fingerprint and current applicable authority/assignment binding. Thus an early pharmacist decision can coexist with a later second-physician decision without circular invalidation. Changing or releasing the assignment revision supporting a recorded approval denies future reliance on that approval while preserving the historical decision; a terminal lane is not reopened through R2 and needs a fresh linked request for another review.

**Logical states (proposed, not new database enums):**

- Request: pending review → decision recorded, rejected, expired, invalidated or cancelled. Emergency second-physician and pharmacist lanes have distinct pending/decision states under one request. Only one terminal decision per lane/evidence round.
- Assignment: unheld → held → released, expired or invalidated. A new held revision can follow only a permitted R2 action on a pending lane. Terminal decision never resets through reassignment. A held assignment may permit scoped terminal readback until expiry/release/authority loss, but no second decision.
- Emergency use: not authorized → bounded simulated authorization after the independent second-physician approval → pharmacist-reviewed continuation or blocked by rejection, expiry, stale evidence or authority loss. These are derived authorization conditions, never real care permissions.

Assignment expiry is no later than request expiry and designation validity; actual bounded lease policy, request TTL and renewal-free recovery design must be settled before Plan approval. No undocumented clinical duration is introduced. There is no assignment-renew action in this candidate: release/reclaim while eligible or takeover after invalidity uses R2, with a new revision and no review-window extension.

Expiry/revocation deny immediately through current read/mutation predicates, even before a background projection catches up. A worker may materialize an already-defined expiry/audit outcome with durable attribution; it cannot invent authorization, extend a lease or provide an undisclosed user action. The authority update path is the versioned deployment input described above, not a hidden revocation endpoint. Plan must prove snapshot/current-revision consistency and failure behavior during configuration propagation.

After rejection, terminal expiry, cancellation or evidence invalidation, do not reopen a lane or edit its signature. The authorized prescriber may correct/rerun and create a fresh linked request with `requestContraindicatedOverride`; all current guards apply and the old record remains immutable. R2 does not provide reconsideration or clinical referral. Loss of reviewer authority after approval denies future reliance on that approval; retain the historical decision and require a new current review/request before affected future signing. No historical clinical action is rewritten.

## 6. Emergency, transaction and failure contract

Emergency request creation commits a durable pharmacist-review obligation immediately, alongside the pending second-physician lane. Its metadata is discoverable by eligible pharmacists without waiting for a successful notification or F014. Pharmacist review can progress independently; it never grants second-physician authority. Early pharmacist rejection prevents emergency authorization. If the pharmacist has already approved on current evidence, the two-physician simulation still requires the independent second decision; ordinary pharmacist-reviewed signing remains the existing normal alternative.

If the request itself expires or is cancelled/invalidated before pharmacist review, retain an explicitly unreviewed blocked obligation, visible as minimum metadata through R1 while the viewer remains currently scoped. Do not relabel it reviewed, drop it because delivery failed or permit a late decision against terminal evidence. The prescriber can initiate a fresh linked request through the existing request operation when still authorized; its review records reference the predecessor without retroactively authorizing the expired event. No new administrative close/reopen action is assumed. Assignment expiry alone on a still-pending valid request instead permits R2 takeover and review of that same obligation.

The second-physician approval is the only proposed activation-authorizing mutation for the emergency simulation; no extra activate button/API exists. Its successful transaction requires the linked durable pharmacist obligation, records the second decision and starts the versioned **60-second virtual-clock test window**. The existing `signPrescription` remains a separate prescriber action and must recheck all guards; second approval does not implicitly sign. The harness controls time in an isolated deployment; a requesting browser cannot set the clock or choose an unrestricted window. No real clinical emergency criteria/window are approved.

If the window ends without current pharmacist approval, deny further simulated emergency signing/continuation. Current pharmacist approval may satisfy the next simulated review gate only while the request/evidence remains otherwise valid; it does not authorize treatment, dispense or administration. Request terminal expiry/rejection, roster loss or evidence change still denies use and requires a fresh linked request/current reassessment. Window expiry alone never generates pharmacist approval or extends a request/assignment lease. Exact physical state encoding and clock observation are Plan responsibilities.

Every state-changing operation must have one linearization point for current authority/version checks and its prescription/request/lane/assignment effects, immutable audit, required durable obligation, outbox and idempotency response. Commit none if a required write fails. A concurrent revocation/evidence change and decision/sign must serialize so that the loser cannot act on a stale authorization. Plan must define lock order/CAS, current roster materialization, actor/operation/key scoping, replay storage, failure ordering and rollback/roll-forward details; no database implementation is chosen by this proposal.

Outbox delivery is an at-least-once hint with bounded retry/deduplication and observable failed-delivery state; it conveys no detail or permission. R1 reads the durable prescribing-owned obligation, not a volatile notification inbox. API and worker ownership, retry/lease/dead-letter monitoring and recovery evidence must be explicit in Plan using existing infrastructure contracts. No new messaging channel, operator replay operation, vendor approval or F012 notification dependency is introduced. If an interactive new recovery capability proves necessary, stop for boundary approval instead of concealing it in a helper.
