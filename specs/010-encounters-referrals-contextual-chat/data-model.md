# Feature 010 data model and transaction design

**Status:** planning design, 2026-09-26; no migration or clinical data was changed. `spec.md`, the dated Feature 010 reconciliation, Data/RLS §17, and the existing Feature 009 appointment/queue migration govern this model. Physical SQL and generated-client parity are implementation evidence under `OPEN-TECH-002`.

## Identity, types, and ownership

All entity identifiers are internal UUIDs; UTC instants cross the API as RFC 3339; mutable rows carry positive monotonic versions. Existing Feature 009 physical columns use appointment `status`, `patient_person_id`, `doctor_person_id`, `fee_minor_units`, `currency_code`, `payment_method`, `source_referral_id`, and queue `state`/`appointment_id`/`queue_scope_id`. The Feature 010 API uses camel-case DTOs but its PostgreSQL adapter maps to those actual predecessor names. No generic service-role online write or new user-facing table grant is permitted.

| Domain area / owner | Planned logical fields and nullability | Constraint and index intent |
|---|---|---|
| `clinical.encounters` / Clinical | `id` UUID PK; non-null `patient_person_id`, `facility_id`, `appointment_id` for Feature 010 rows, `responsible_clinician_id`, `encounter_type`, `status=open|completed`, `started_at`, `version`; nullable `ended_at`, `completion_summary`; optional `condition_ids`, `observation_ids`, `order_ids` as `0..n` UUID reference collections | General canonical model keeps `appointment_id` nullable for future use, but the Feature 010 creation entry point requires it. Partial unique `(appointment_id) WHERE status='open'`; index patient/facility/start and appointment. `completed` requires nonblank summary and end time; `open` has neither. Reference collections default empty, deduplicate IDs, and validate current same-patient source rows if present; no new referenced-resource lifecycle is created. |
| `clinical.encounter_participants` / Clinical | Composite identity of `encounter_id`, `person_id`, `role_code`, `started_at`; nullable `ended_at`; non-null UTC start | FK to encounter and internal person; interval end after start; partial unique active `(encounter_id,person_id,role_code) WHERE ended_at IS NULL`; active interval lookup by encounter/person. `createEncounter` inserts exactly one initial active interval for the responsible clinician derived server-side from the linked appointment and current authorized treating-clinician context. `updateEncounter` may end only a current non-responsible interval while open; no Feature 010 participant-add path exists. Patient participation is derived from the linked appointment, not a workforce row. |
| `clinical.clinical_notes` / Clinical | UUID PK; non-null `encounter_id`, `author_person_id`, `note_type`, encrypted `body`, `visibility_code=private|patient_visible`, `signed_at`; nullable `supersedes_id` | FK to encounter and prior same-encounter note for correction; append-only row, no UPDATE/DELETE online grants. Nonblank body is structural validation only, not clinical sufficiency. Indexed by encounter/signed time and supersession. Current authorization and the approved signer rule are checked again at signing; historical version/visibility stays immutable. |
| `clinical.conditions` / Clinical | UUID PK; non-null patient, code system/code, bilingual display and clinical/verification status; onset/abatement, recorder/verifier and pending-standardization fields according to canonical Data/RLS | Patient-scoped code/status checks; index patient/code/status. Feature 010 only associates already existing same-patient conditions with an encounter; there is no condition create/update operation or new clinical threshold. No condition is required for completion. Exact code set remains governed by canonical data and later clinical review. |
| `clinical.referrals` / Clinical | UUID PK; non-null `source_encounter_id`, patient/requester, target specialty, `reason_summary`, `status=pending|accepted`, `version`; nullable target facility/doctor and `resulting_appointment_id` while pending; accepted field-code selection and attributable accepting actor/time become non-null on acceptance | FK to source encounter and resulting appointment when accepted; one resulting appointment per accepted referral; unique resulting appointment link; status check and immutable accepted disclosure selection. `pending` has no target disclosure. Selection is exactly `reason_summary` plus optional source `encounter_type`; no note/condition/observation/order body field. Index source/patient/status and permitted target facility/status. |
| `trust.messages` / Trust | UUID PK; non-null `context_type=appointment`, linked `context_id`, `sender_person_id`, encrypted body, `sent_at`; `attachment` SQL `NULL`; canonical edited/deleted markers retained but not mutated by Feature 010 | FK or validated existing appointment context; check `attachment IS NULL` on Feature 010 inserts, nonblank body, index context/sent time/ID for cursor order. Context expiry is an authorization cutoff, not deletion or a guessed retention period. No edit/delete operation. |

Reference collections in `clinical.encounters` are planning storage mapping within the six canonical areas, not new clinical facts. Implementation must verify same-patient existence and revoke a stale cross-patient reference atomically; no absent reference blocks completion. If physical migration review determines another representation is needed, it requires a compatible `OPEN-TECH-002` parity review before implementation, with no scope or API change.

## State machines and invariants

| Existing operation | Required locked before-state | Atomic after-state / prohibited result |
|---|---|---|
| `createEncounter` | Existing Feature 009 appointment `checked_in`, matching unique queue entry `called`, same patient/facility/doctor context, no open encounter for appointment | One `open` encounter and exactly one server-derived responsible-clinician interval; appointment `in_consultation`; queue `in_service`. Client workforce IDs, missing queue, mismatch, stale state or duplicate: no change. |
| `updateEncounter` | Encounter `open`, current version, currently authorized treating CLN | Structured same-patient references and end of a current non-responsible participant interval only; version increments. Participant-add property or attempted responsible-clinician end denies. No signed-note or predecessor status mutation. |
| `signEncounterNote` | Current authorized treating CLN; correction signer is original author or current responsible clinician; superseded row signed and same encounter | New immutable signed version. Prior row/body/visibility unchanged. |
| `completeEncounter` | Encounter `open`, linked appointment `in_consultation`, queue `in_service`, responsible clinician, current version, nonblank authored summary and true structural confirmation | All three `completed`, encounter ended time and summary set, current context access ended. `0..n` absent condition/observation/order references are valid. |
| `createReferral` | Authorized source encounter and treating clinician | Internal `pending` referral; resulting appointment null; no target disclosure. |
| `acceptReferral` | Current `pending` referral/version; PAT self or live-authorized GUA/DEL; selected fields exactly match pending preview; slot specialty and each specified target doctor/facility match current authoritative Feature 009 eligibility and slot/version | One `accepted` referral, one confirmed server-priced EGP/cash appointment linked through `source_referral_id`, accepted selection/actor/time evidence and target projection, all atomically. Conflict, target mismatch or lost authority: none. Specialty-only permits any currently eligible verified doctor/facility in that specialty; matching asserts routing, not clinical appropriateness. |
| `listContextMessages` / `sendContextMessage` | Linked appointment in `in_consultation`, encounter `open`, current subject PAT or workforce active interval | Authorized history/body append only. Participant interval end or completion denies both immediately, including old history. |

All unspecified transitions deny. Feature 009's own producers are unchanged: check-in stops at appointment `checked_in` plus queue `waiting`, and queue call advances only `waiting` to `called`. Feature 010 extends state guards only for its two named encounter operations. Appointment `no_show`, other queue states, and unlinked encounters have no Feature 010 producer.

## Transaction boundaries, locks, and deterministic conflicts

1. For each of the seven `I` mutations, lock the principal/route/key/body-hash idempotency record first. Same key/body returns the stored canonical result; changed body returns `idempotency-key-reused`; in-progress replay cannot produce a second effect.
2. `createEncounter`: lock appointment, matching queue and open-encounter uniqueness scope in stable order; recheck current CLN license/membership/care/purpose/AAL, patient/facility/doctor equality and both before-states. Derive the responsible clinician from the linked appointment and current authorized treating-clinician context; reject client workforce IDs. Insert encounter and only that clinician's active interval, advance both predecessor rows, audit, approved minimum outbox marker and stored response in one transaction. Physical state guard permits this producer only.
3. `updateEncounter`: lock encounter/version and affected participant intervals; recheck current action; validate each existing same-patient reference; end only a current non-responsible interval after explicit clinic UI confirmation, or apply permitted structured facts, and increment version in one transaction. The responsible interval cannot end while open; participant-add properties deny. An ended interval loses authorization before commit becomes visible. Invalid interval or stale `If-Match` denies.
4. `signEncounterNote`: lock encounter and optional superseded note; recheck signer and same-encounter immutable history; insert encrypted signed version, minimum audit and stored idempotency result. Reject correction of an unrelated note.
5. `completeEncounter`: lock encounter, appointment, queue and active context authorization scope in stable order; recheck responsible clinician and exact before-state triple. Store summary and complete all three with one audit/outbox/idempotency result; no partial completion. Message reads/sends after commit fail current-context checks.
6. `acceptReferral`: in its own route/actor/key/body-hash idempotency scope, claim/check the key, then lock the pending referral/version, recheck current PAT/GUA/DEL relationship/grants, and validate selected disclosure and target. Match slot specialty and each present target doctor/facility against the referral and authoritative Feature 009 verified eligibility; reject mismatches before booking. Under the existing Feature 009 schedule/availability/doctor/exclusion lock order, invoke the internal composable booking primitive; link its confirmed appointment by `source_referral_id`, mark the referral accepted with selected fields/actor/time, write one acceptance audit/outbox/canonical response, then commit. Client supplies no fee, currency or payment mode. The primitive derives fee and fixes EGP/cash_on_arrival. Unique/exclusion/version or authority failures roll back every effect, including appointment, referral transition and operation records; no premature target disclosure.
7. `sendContextMessage`: recheck eligible current appointment/encounter and participant interval under a lock compatible with interval ending/completion; insert only encrypted body with SQL-null attachment. The read path rechecks the same facts per page and never trusts a realtime event or cached projection.

Use the existing request transaction context and fixed-`search_path` narrow helpers. Never make an online user operation as table owner, service role, or `BYPASSRLS`. The chosen stable lock order must be proved with concurrent opposite-order synthetic tests before migration approval.

The internal booking primitive is one composable transaction participant, not an eleventh API operation. It owns the existing Feature 009 current schedule/time/fee/exclusion checks and appointment insertion; it writes no operation-level idempotency, audit, outbox or canonical response record. Feature 010 supplies two additional preconditions to that primitive: compare `availabilityVersion` with the selected schedule's `version` under lock, and prove the exact start/end/timezone/civil-date tuple appears in current authoritative Feature 009 effective availability, including weekly windows and exceptions. Current verified doctor/facility/specialty routing eligibility is checked in the same acceptance transaction before insertion. The external Feature 009 `createAppointment` request has no `availabilityVersion`, so its wrapper invokes the primitive without these Feature 010-only preconditions and retains its current schedule/time/exclusion behavior. GiST exclusion remains the final one-winner guard for both paths. A forward Feature 010 migration refactors the existing `clinical.create_appointment_v1` wrapper to call it while preserving `createAppointment` request/result/errors, server-priced fee, EGP/cash, replay and one-winner behavior. That wrapper retains its own F009 operation records. Do not edit the historical Feature 009 migration. Prove both wrappers and the primitive with serial/concurrent real-Postgres regression vectors before rollout.

## Per-action API and forced-RLS matrix

`ENABLE` and `FORCE ROW LEVEL SECURITY` apply to every new domain table, with default deny and only narrowly granted entry functions/views. RLS is an independent boundary; a row grant never implies a free-text column grant. All predicates re-evaluate current actor, subject, action, facility, care purpose, AAL, relationship/license, and state as applicable.

| Operation | Table action and current predicate | Allowed projection / negative proof |
|---|---|---|
| `createEncounter` | Insert encounter/initial intervals and update only linked appointment/queue after current licensed treating CLN and locked checked-in/called scope | No other-patient/facility insert, missing queue, duplicate open encounter or unlinked path. |
| `getEncounter` | Select encounter and permitted child rows for PAT self, GUA current guardianship with record scope, DEL current `record.view`, or current treating CLN | Patient/representative receive released fields and `patient_visible` notes only; `private` requires current treating care team. |
| `updateEncounter` | Update only open encounter and workforce intervals for current treating CLN at facility under version | Ended interval grants no further chat; cross-patient reference and completed edit deny. |
| `signEncounterNote` | Insert note for current authorized treating CLN; correction also author-or-responsible rule | Append only; private body excluded from patient/representative/referral projections. |
| `completeEncounter` | Update linked triple for current responsible clinician with exact before-states and version | No partial triple transition or missing-summary bypass. |
| `createReferral` | Insert pending referral by current treating CLN for source encounter | Source care and currently authorized subject preview only; target denied while pending. |
| `listReferrals` | Select PAT own, GUA active approved, DEL both `record.view` and `appointment.manage`, source CLN treating/action, or target CLN accepted+linked-target-appointment/current membership/action/purpose | Every page rechecks authority and projects only actor-allowed fields; target never sees pending or unselected content. |
| `acceptReferral` | Update pending referral and insert Feature 009 appointment for PAT/GUA/DEL under current live grant and target slot version | Exact selected two-field maximum; no inferred consent, CLN acceptance, or stale booking. |
| `listContextMessages` | Select appointment-context messages for linked subject PAT or workforce with active encounter interval while open/in consultation | GUA/DEL, ended interval, completed context, unrelated patient deny even for history. |
| `sendContextMessage` | Insert one body-only appointment-context message under same live predicate | Reject any attachment property, null included; no offline, ended or completed send. |

## Encryption, events, retention, migration and rollback

- Note and message bodies use the existing designated encryption/key adapter; transport uses TLS; API projections never expose ciphertext or private body outside its current role. Completion summary and referral reason are sensitive, purpose-limited data. Audit/outbox/log/metric payloads carry no raw note, summary, reason or message text.
- Minimum audit records actor, purpose, patient/facility scope, action, outcome, request ID and UTC time; denied actions record only policy-required security evidence. Existing outbox ordering is by aggregate and version; planned marker families are encounter opened/completed/participant changed, note signed, referral pending/accepted, and context message created. Payload is IDs, scope, state/version and correlation only; event names/mapping are internal, not new API operation IDs or patient-facing notifications. No template/channel is enabled without separately approved bilingual governance.
- Retention class links are required, but `OPEN-LEGAL-002` leaves durations and disposal automation unset. Completion cuts off message access without deleting retained history. No production PHI processing while `OPEN-LEGAL-001/002/007` apply.
- Migration plan: forward additive tables/columns/functions/indexes, exact state-producer extension and composable booking refactor; leave historical Feature 009 migrations untouched. Validate existing appointment/queue rows and fee/exclusion constraints first; add forced-RLS policies and function EXECUTE grants under non-owner identity; compare catalog/spec/OpenAPI/contract types; backfill nothing with fabricated clinical data. Run synthetic restore, migration idempotence, F009 `createAppointment` wrapper parity (request/result/problem, fee, replay, slot race), and downgrade/roll-forward evidence. Append-only signed notes and accepted disclosure/audit cannot be destructively rolled back; disable Feature 010 entry paths and roll forward any data correction. Exact DDL, predicate proofs and generated clients remain `OPEN-TECH-002` implementation artifacts.
