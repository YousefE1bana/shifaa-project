# Feature 010 planning research — 2026-09-26

This is Phase 0 design research for the approved Feature 010 specification. Decisions below implement the dated Product Owner/Architecture reconciliation; they do not approve physical migrations, generated clients, UI compositions, clinical content, or production processing. All examples and later verification use synthetic patients.

## Decision 1 — Reuse the Feature 009 state boundary

- **Decision:** `createEncounter` locks the current appointment and its unique matching queue entry and changes `checked_in`/`called` to `in_consultation`/`in_service` in the same transaction as one `open` encounter and one server-derived responsible-clinician workforce interval. A missing queue or client-supplied workforce identity denies the whole operation. `completeEncounter` locks the same triple and changes `open`/`in_consultation`/`in_service` to `completed`/`completed`/`completed` only after the responsible clinician supplies a nonblank authored summary and explicit structural confirmation. Conditions, observation references, and order references are independently `0..n` and cannot block completion when absent.
- **Rationale:** Feature 009 deliberately ended its producers at check-in and queue call; it did not create encounters or produce consultation/service states. The current Feature 010 reconciliation assigns the two transitions to its existing operations. Source: `specs/009-clinic-scheduling-appointments-queue/spec.md` state table; `docs/architecture/SHIFAA-Data-RLS.md` §17; `docs/governance/SHIFAA-Feature-010-Reconciliation-2026-09-26.md`.
- **Alternatives rejected:** creating an unlinked encounter, allowing a missing queue, or adding a queue/appointment operation would violate the approved boundary.

## Decision 2 — Preserve Feature 009 booking authority for referral acceptance

- **Decision:** Refactor the existing Feature 009 `createAppointment` wrapper in a forward Feature 010 migration to call one internal composable appointment-booking primitive. This is not an API operation. The primitive owns authoritative current schedule/slot, optional expected schedule version, time/exclusion/one-winner concurrency and server fee guards, but writes no operation-level idempotency, audit, outbox or canonical response record. The externally unchanged `createAppointment` wrapper continues to own those records for its own route. `acceptReferral` checks current verified doctor/facility/specialty routing eligibility in the same transaction, then calls the primitive. It owns a separate idempotency scope and one transaction: claim/check key, lock pending referral, recheck current subject authority, validate accepted fields and target, invoke the primitive, link `source_referral_id`, mark accepted, write its own audit/outbox/canonical response, then commit. Any failure rolls back referral, appointment and operation records together. The referral request supplies no fee, currency or payment mode; the server derives the authoritative fee and fixes `EGP`/`cash_on_arrival`.
- **Target matching:** The selected slot must match the referral specialty. A specified target doctor and/or facility must each match exactly; with specialty alone, any currently eligible verified doctor/facility in that specialty may be selected. Validate this against authoritative Feature 009 data before invoking the booking primitive; a mismatch creates no appointment. This validates routing only, without asserting clinical appropriateness.
- **Version and effective-slot compatibility:** Feature 009 discovery `availabilityVersion` is the selected schedule's `version`; its external `createAppointment` request does not carry that field. Feature 010 passes an expected schedule version and requires the exact selected time/timezone/civil-date tuple to be present in current authoritative Feature 009 effective availability under the schedule lock, including window/exception effects. The existing Feature 009 wrapper invokes the primitive without those Feature 010-only preconditions, preserving its external behavior and current schedule/time/exclusion guards. GiST exclusion remains the final one-winner guard. Feature 010 also checks current verified doctor/facility/specialty eligibility in the same transaction.
- **Rationale:** The current `clinical.create_appointment_v1` combines booking guards with operation records and therefore cannot be called unchanged inside `acceptReferral` without a second idempotency/audit/outbox scope. Its current schedule-derived fee, exclusion, version and `source_referral_id` behavior must be preserved through the wrapper. Source: Feature 009 `data-model.md`, `contracts/openapi.yaml`, and `supabase/migrations/20260912000900_clinic_scheduling_appointments_queue.sql` `clinical.create_appointment_v1`; Feature 010 reconciliation and spec §§5–7.
- **Alternatives rejected:** direct appointment insert, client fee/currency selection, slot holds, a separate booking operation, or disclosure before acceptance.

## Decision 3 — Six data areas, append-only notes, and scoped disclosure

- **Decision:** Plan only `clinical.encounters`, `clinical.encounter_participants`, `clinical.clinical_notes`, `clinical.conditions`, `clinical.referrals`, and `trust.messages`, with existing Feature 009 appointments/queue as dependency rows. Encounter state is `open|completed`, referral state is `pending|accepted`, note visibility is `private|patient_visible`. Signed-note correction appends a signed superseding row. A pending referral is internal; an accepted referral discloses only `reason_summary` plus optionally the source `encounter_type` explicitly selected by PAT/GUA/DEL. No note body enters the referral.
- **Rationale:** This is the roadmap/PRD/Data-RLS and approved reconciliation field set. Physical SQL naming must align with the implemented Feature 009 appointment `status`, `patient_person_id`, `doctor_person_id`, `fee_minor_units`, `currency_code`, `payment_method` and queue `state`; the logical API contract remains in `contracts/openapi.yaml` here. Source: `docs/governance/SHIFAA-Remaining-Specs-Roadmap.md` Feature 010; `docs/architecture/SHIFAA-Data-RLS.md` §§3,17; Feature 009 migration `supabase/migrations/20260912000900_clinic_scheduling_appointments_queue.sql`.
- **Alternatives rejected:** a third visibility class, mutable signed note, automatic private-note share, new clinical state, and a new independent observation/order lifecycle.

## Decision 4 — Live representative and context authorization

- **Decision:** Every referral read and accept independently rechecks PAT self, current active approved GUA guardianship, or DEL with both current `record.view` and `appointment.manage`; source CLN requires current treating/facility/action/purpose, while a target CLN receives only an accepted referral linked to a target-facility appointment and only its accepted field selection. Encounter record projections use their separate current record grants. Subject PAT may read/send appointment-context messages while the linked encounter is open and appointment in consultation; workforce needs an active `encounter_participants` interval. Under the final 2026-09-26 participant disposition, `createEncounter` opens only the server-derived responsible-clinician interval and `updateEncounter` may end a current non-responsible interval; Feature 010 has no participant-add input or UI. GUA/DEL never chat in Feature 010. Every read/send checks the interval and context again; ending an interval or completion cuts off history and sends immediately.
- **Rationale:** Stale JWT claims and realtime events are not authorization. API and forced RLS must independently apply current facts, with non-owner execution and default deny. Source: Feature 010 spec §6 action matrix, Data/RLS §§12,17 and Constitution Articles I, III–V, IX.
- **Alternatives rejected:** relationship-inferred chat or referral consent, staff access by facility alone, stale client authorization, or a general consultation channel.

## Decision 5 — Exact body-only messaging and UI placement

- **Decision:** The only Feature 010 context type is the appointment linked to an eligible encounter. `sendContextMessage` accepts a nonblank body and rejects the presence of an `attachment` property even when its JSON value is null; storage attachment remains SQL `NULL`. Patient composition appears only inside existing `/encounters/:id`; patient `/records` owns pending referral preview/acceptance; clinic `/referrals` owns creation/tracking; clinic `/messages` requires an eligible selected appointment context. Reconnect uses authoritative REST reauthorization/reconciliation and a stale/last-updated state. No offline clinical write queue.
- **Rationale:** These placements and prohibitions are explicit in the reconciliation and UI Contract. The later 2026-09-26 Product Owner + Acting Design Lead decision approves the exact Feature 010 TEST-ONLY functional composition/baseline under `OPEN-UX-001`; `OPEN-UX-002` verification remains separate. Source: `docs/design/SHIFAA-UI-Contract.md` §8 and Feature 010 paragraph; Feature 010 spec §§3,8; dated Feature 010 baseline decision packet.
- **Alternatives rejected:** patient inbox, upload intent, order/prescription chat, general consultation, or copying Feature 009 visual approval.

## Decision 6 — Contract, events, and gate effects

- **Decision:** This plan's OpenAPI 3.1.1 is the exact **planning** wire contract for the ten existing operation IDs, with closed request schemas, actor-projected responses, RFC 9457 errors, `Idempotency-Key` on the seven catalogued `I` mutations, `If-Match` on the three `V` mutations, and bounded cursor reads. Implementation must generate its single source of truth and clients from `packages/contracts`, prove parity, and deliver physical DDL/RLS under `OPEN-TECH-002`; this plan artifact itself does not close that gate. Domain mutation, minimum attributable audit, minimum-ID outbox marker where an approved delivery path exists, and completed idempotency response share one transaction. Realtime notifications carry no clinical body and never grant access. No new patient notification template/channel is authorized.
- **Rationale:** API Catalog §1/§4, Architecture §§3,6–7, Master §11.2 and Feature 010 spec §§7,9 require those semantics. The existing Feature 009 plan OpenAPI is predecessor reference, not a new operation source.
- **Alternatives rejected:** handwritten divergent client, service-role online bypass, raw free text in event/log, or treating plan schemas as implementation evidence.
