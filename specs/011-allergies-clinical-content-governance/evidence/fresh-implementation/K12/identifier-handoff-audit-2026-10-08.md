# Feature 011 K12 identifier handoff audit

Date: 2026-10-08 (Africa/Cairo). Result: **BASELINE_RECONCILIATION_REQUIRED**.

Authority: direct Product Owner instruction `K11_ACCEPTED + K12_IDENTIFIER_HANDOFF_REMEDIATION_APPROVED`. This is a diagnostic report, not an amendment, architecture decision, lifecycle restart, or authorization to change a contract. K11 acceptance is recorded separately. K12 remains unaccepted.

## Exact missing handoff

The existing screens do not receive a server-issued pair tying their selected Feature 010 `identity.people.id` to the Feature 011 `identity.patients.id`. The clinic flow also needs the already-authorized current encounter/facility context tied to that same pair. Internal SQL resolution exists; the gap is its delivery through an approved public projection and then through the existing screen context.

`data-model.md:9` requires explicit `identity.patients.person_id` resolution and same-patient encounter binding. The identity baseline creates independent patient UUIDs and a unique `person_id` FK (`supabase/migrations/20260811000100_identity_onboarding_baseline.sql:37`). UUID syntax cannot supply the relationship. The Feature 011 route remains `/patients/{managedPatientId}/allergies` for its existing read/create operations.

## Ranked minimum safe reconciliation options

These are prospective options for Product Owner/baseline-owner reconciliation. **None was implemented or approved by this audit.** Both keep the seven Feature 011 operations and their managed-ID route meaning unchanged.

1. **Amend the existing identity, relationship and encounter projections with explicit identifier pairs (preferred).** Supply the self managed ID with the existing authenticated self profile. For an already-authorized GUA/DEL record context, bind the existing F004 managed ID to the subject person ID in a minimum record-read projection, conditional on current `record.view` authority; do not repurpose `actor_person_id` or expand ordinary relationship-view disclosure. Add the managed ID to the current authorized F010 encounter projection, retaining the existing person ID, encounter ID and facility ID. Carry only a freshly server-issued same-subject context into the existing routes. Reauthorize at every read/write; the pair conveys no clinical or administrative authority.
   - Canonical changes requiring approval: a new dated governance reconciliation/amendment record; `docs/architecture/SHIFAA-API-Catalog.md` for `getMyProfile`, relevant F004 record-context projection and `getEncounter`; `docs/architecture/SHIFAA-Data-RLS.md` for minimum disclosure/current authorization; `specs/001-identity-onboarding/contracts/openapi.yaml` (`Profile`); `specs/004-family-care-relationships/contracts/openapi.yaml` (`Relationship`/scoped response); `specs/010-encounters-referrals-contextual-chat/contracts/openapi.yaml` (care-team/subject encounter projection). Supporting predecessor design/traceability amendments and the F011 Plan/UI handoff detail would need explicit owner approval. Corresponding contracts/clients must then be updated through their repository workflows. No F011 OpenAPI change or new privilege is proposed.
2. **Use the existing F009 appointment projection as the clinic mapping carrier.** Use the same self/F004 reconciliation above, but add the explicit managed ID beside the unchanged person ID in authorized `getAppointment`/`listAppointments` projections. The clinic must separately receive and freshly read an already-authorized F010 encounter, verifying its person/facility against the appointment and pair. A checked-in appointment or queue entry alone cannot authorize an allergy operation; without a current encounter, fail closed. This touches more appointment producers and consumers and is less narrowly aligned with F011's current-care requirement.
   - Canonical changes requiring approval: the same self/F004/governance/API/Data-RLS amendments, replacing the F010 identifier-field amendment with `specs/009-clinic-scheduling-appointments-queue/contracts/openapi.yaml` (`Appointment` and operations returning it), predecessor design/traceability and approved F011 UI/Plan handoff detail. Existing F010 context consumption still needs explicit handoff/revalidation; no new encounter lifecycle or authority is proposed.

For either option, refresh the affected normative/generated input hashes and obtain the applicable lifecycle approval before implementation. Revalidate affected predecessor authorization, current F011 parity and K11/K12 proofs as required; preserve existing acceptance history. A header side channel, frontend database query, deterministic UUID transformation, hardcoded fixture mapping or new unapproved resolver endpoint is not a reconciliation shortcut.
