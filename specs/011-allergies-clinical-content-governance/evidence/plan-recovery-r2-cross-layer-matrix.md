Common exact owners: canonical response serialization and protection = trusted service; authoritative version/status/time/receipt tuple/CAS = SQL; protected storage/COMMIT guard = narrow SQL finalizer; replay authorization = native/current API plus current DB action/receipt scope; replay decryption = prepared local service capability. External evidence/key/network work is always outside DB locks; only bounded LOCAL receipt crypto is the under-lock exception. A competing preflight can encrypt but cannot commit a losing effect; known committed replay never encrypts. No acceptance owner can pick a serialization/storage/lock/allocation policy hidden in historical Tasks.

## Remaining incomplete cells — R2-SD-04

For signClinicalContentRelease, the public request/response and required actor/capacity/decision/artifact checks are explicit, but the exact trusted external-signing verification result supplied to SQL is not defined. The restricted signature-binding sidecar remains only a prose requirement in data-model §4: no closed external-evidence reference/result binding or typed persistent mapping to the mandatory SignatureEvidence.evidenceRef is specified. These are incomplete exact-input, trust/validation and persistent-representation cells. publishClinicalContentRelease and governance signature projections depend on that immutable binding. P4 cannot invent it; P6 tests cannot retroactively define it. See the [root self-debate](plan-recovery-r2-self-debate.md) for the evidence and minimum correction. All other rows are design coverage, not runtime acceptance.
