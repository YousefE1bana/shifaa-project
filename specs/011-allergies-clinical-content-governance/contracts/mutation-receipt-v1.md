# Feature 011 atomic durable mutation receipt v1

Recovery R2 internal design; review required; implementation fully paused. `SHIFAA-F011-RECEIPT-PROTECTED/1` and `SHIFAA-F011-RECEIPT-AAD/1` apply to all five existing mutations, not to read lists or predecessor receipts. No new operation/route, PostgreSQL crypto, clinical enum or vendor is introduced. The existing baseline transaction invariant is preserved.

## One transaction, two private SQL phases, one committed result

1. Before a new attempt, verify native session/current action, examine any same-key committed/in-progress/unknown result first. Complete all required domain preflight, Evidence Port work and protected allergy/release preparation outside locks. For create/publish, pre-resolve/verify exact required artifactReview material under its separate disclosure rule. Prepare a receipt-protection capability for an exact immutable/versioned keyRef outside the transaction; any KMS/HSM/network operation finishes now. No authoritative response body exists yet.
2. Enter ONE connection/ONE PostgreSQL transaction. Set only already-verified transaction-local context; claim/lock existing idempotency principal/method/template/key/request scope first. Preserve the existing normalized request bindings, If-Match, facility/encounter selectors and baseline in-progress/key-conflict behavior. No separately committed Feature-011 domain effect or durable plaintext preparation.
3. Narrow SQL domain entrypoint locks/revalidates the current domain/authority/lineage/CAS facts in the exact data-model order. It applies the intended effect, appends minimum audit/outbox evidence, and inserts an internal commit obligation describing the authoritative result. It returns only authoritative structural result metadata/opaque stored fields to the trusted repository on this SAME connection. It does not return plaintext clinical facts/material; the service already holds authorized plaintext from preflight and combines it with locked authoritative IDs/times/versions/signature metadata.
4. Service validates that composition against the current generated public response schema. Canonical response serialization belongs to the trusted service: use the compact recursive-key-sorted UTF-8 JSON rule in [allergy protection v1](allergy-protection-v1.md), applied to the unchanged complete response object. Arrays retain authoritative order; timestamps/UUIDs/ETag values come from the SQL result and existing generated format, never local replacements. The exact body bytes, original response status and allowed header tuple are fixed for this result. No plaintext response body/header dump is a SQL argument/log/audit/outbox field.
5. Encrypt the exact canonical body bytes LOCALLY with the pre-prepared capability, fresh random 12-byte nonce, AES-256-GCM and receipt AAD below. This bounded local receipt operation is permitted while transaction locks remain held; it performs NO network, KMS/HSM, evidence resolution or new key lookup. Domain facts/body protection and review resolution remain before locks. Any local serialization, schema, nonce/encryption, insert or completion failure rolls back the ENTIRE transaction, including domain/audit/outbox/obligation/idempotency effects.
6. Invoke the narrow internal receipt-finalization SQL phase on the SAME transaction/connection. It inserts the five-field opaque receipt, validates it against the locked authoritative obligation, and sets existing idempotency completed/status plus an opaque receipt pointer. Only then COMMIT once. Deferred database enforcement below forbids an API process from committing after phase 3 without phase 6. No direct receipt DML grant is added to shifaa_api.
7. After commit, send exactly the same status, canonical bytes and allowed headers. Do not run framework serialization again with different keys/escaping, reread a newer resource, resolve material again for this already-authorized immediate response, or manufacture success before COMMIT is known. Transport loss after commit is handled by stored receipt replay, never another effect.

These are private repository/SQL phases, not extra public operations. Existing mutation entrypoint names/public wire inventory remain. Signing returns SignReleaseResponse; create/verify allergy return AllergyRevision; create/publish release return GovernanceRelease including required authorized artifactReview. There is no evidence-port dependency during locked serialization: all exact review/facts/reason bytes were authorized/prepared before entry, and their immutable bindings are revalidated under locks.

## Exact envelope, typed storage and metadata

Envelope is closed {contractId:SHIFAA-F011-RECEIPT-PROTECTED/1,keyRef,nonce,ciphertext,authTag}. AES-256-GCM only, no algorithm agility. keyRef is nonempty exact strict UTF-8 without NUL, immutable/versioned KMS/HSM reference verified by the trusted producer; mutable current/latest aliases and key material are invalid. SQL performs structural validation only. nonce=12 octets, ciphertext nonempty, authTag=16 octets. Internal JSONB byte carriers may use lowercase even-length hex decoded once; persistence is typed, not a serialized envelope.

`clinical.mutation_receipts` is append-only with these exact NOT NULL envelope columns: receipt_contract_id text, receipt_key_ref text, receipt_nonce bytea, receipt_ciphertext bytea, receipt_auth_tag bytea. Structural constraints mirror the envelope. Its exact immutable non-cryptographic columns are id uuid PRIMARY KEY; idempotency_record_id uuid UNIQUE/FK platform.idempotency_records; actor_person_id uuid/FK identity.people; operation_id text from the five mutation IDs; resource_type text = clinical.allergy_revision or clinical.content_release; resource_id uuid (stable allergy ID for allergy mutations, release ID for content mutations); resource_version integer positive; response_status smallint; response_etag text; response_language text; response_request_id uuid; occurred_at timestamptz. All NOT NULL. The allergy resource_id is the stable assertion ID, while the canonical body contains its exact revision ID; resource_version identifies that revision. Content resource_version is the returned workflow-version SNAPSHOT, not a lookup of mutable current workflow. The entire signature/artifact information is authenticated inside ciphertext. Receipt rows and metadata cannot UPDATE/DELETE.

Allowed replay headers are exactly X-Request-Id = original response_request_id, Cache-Control = private, no-store, ETag = quoted response resource version, Content-Language = original ar-EG/en-EG. Generated success schemas permit these headers; v1 service emits all four. Content-Type = application/json is a fixed transport constant. Status is 201 for createAllergy/createClinicalContentRelease and 200 for verify/sign/publish. No Set-Cookie, Authorization, storage URL, BODY/allergy keyRef or arbitrary response header is stored/replayed. There is no free-form response_headers column; the four headers reconstruct from the immutable typed tuple/constants. Changing current requested locale does not retranslate a stored original response. Request binding/reuse behavior remains the existing public idempotency contract.

Private receipt keyRef is durable crypto metadata only. It never appears in public DTOs, generic platform response metadata, audit/outbox/logs/telemetry. Plaintext clinical response, including authorized artifactReview, is transient; only receipt ciphertext enters SQL. Platform response_body contains exactly {featureReceiptId:canonical receipt UUID}; response_status matches the receipt; generic response_headers contain no clinical values or crypto references. This feature-scoped pointer does not change predecessor idempotency responses or public shape.

## Authoritative commit obligation and physical enforcement

`clinical.mutation_commit_obligations` is a private append-only supporting table, one row per accepted Feature-011 mutation, NOT a second receipt/body or business resource. Exact NOT NULL fields: idempotency_record_id uuid PRIMARY KEY/FK platform.idempotency_records; receipt_id uuid UNIQUE; actor_person_id uuid/FK identity.people; operation_id text; resource_type text; resource_id uuid; resource_version integer; response_status smallint; response_etag text; response_language text; response_request_id uuid; audit_event_occurred_at timestamptz; audit_event_id uuid; outbox_event_id uuid/FK platform.outbox_events; occurred_at timestamptz. The audit FK is the actual partition-compatible composite (audit_event_occurred_at,audit_event_id) -> audit.events(occurred_at,id), not a nonexistent globally unique audit ID. Metadata constraints match receipt above. SQL allocates receipt_id and response tuple after the authoritative effect; language/original request ID are validated trusted request context captured for this attempt. One obligation row, one receipt, one completed scope. No plaintext clinical payload or keyRef in this table.

Domain entrypoints require their locked idempotency record, insert the obligation before returning and cannot expose a raw write path bypassing it. Finalization verifies every shared tuple value exactly, actor/principal scope, operation/hash binding and SQL-owned status/ETag/resource result; it cannot accept a client-selected response tuple. Receipt FK to its obligation plus unique idempotency binding prevents substitute receipts. An INITIALLY DEFERRED constraint enforcement at COMMIT requires each obligation's receipt to exist with exact matching tuple, referenced audit/outbox evidence to exist for that effect, and matching platform idempotency to be completed with that receipt pointer/status. Missing finalization, incomplete state, wrong metadata, deleted receipt or missing effect evidence aborts COMMIT. Corresponding deferred checks on Feature-011 completion prevent a completed pointer without an obligation/receipt. Narrow executor is non-owner/NOBYPASSRLS, and tables ENABLE + FORCE RLS; immutable guards and minimum grants protect both tables. Any guard failure rolls back, not an application-only warning.

Receipt/body authenticity remains trusted application-producer proof: SQL cannot authenticate GCM or inspect the plaintext. Physical structural acceptance is not permission to call a public endpoint before the real service producer/schema/crypto composition is accepted. Synthetic physical fixtures may exercise the commit/finalization protocol without claiming AES-GCM proof. Receipt/obligation/idempotency FKs use RESTRICT, not cascade deletion. The Feature-011 wrapper does not run the predecessor generic expired-record purge against these linked clinical scopes or infer a committed effect absent from expires_at. Production retention/deletion remains OPEN-LEGAL-002; no new duration is selected. Baseline receipt cleanup for unrelated operations is unchanged.

## Deterministic AAD

Prefix `SHIFAA-F011-RECEIPT-AAD/1;` followed by exactly twelve non-null UTF-8 octet-length `S<byte-length>:<payload>,` frames:

1. resourceType = clinical.mutation_receipt
2. receiptId = receipt.id canonical lowercase UUID
3. idempotencyRecordId = authoritative locked platform record UUID
4. operationId = one of the five existing mutation IDs
5. targetResourceType = receipt.resource_type
6. targetResourceId = receipt.resource_id canonical UUID
7. responseResourceVersion = positive minimal decimal receipt.resource_version
8. responseStatus = minimal decimal 200 or 201, consistent with operation
9. responseETag = exact quoted response_etag, consistent with version
10. responseLanguage = exact original ar-EG/en-EG
11. responseRequestId = original response_request_id canonical UUID
12. keyRef = receipt_key_ref exact immutable versioned reference

No escaping beyond framing, Unicode normalization, locale, whitespace conversion, null frame or independently persisted AAD. All reconstruct from immutable receipt/obligation tuple plus constants. Authenticated status/header tuple prevents ciphertext substitution across identities/scopes/operations/resources/versions/status/permitted replay metadata. The idempotency FK and immutable completed scope/request-hash/principal tuple are checked at finalization and replay. Current authorization, current resource head/workflow, mutable session state and current locale are NOT reconstructed as cryptographic identity. The recorded workflow snapshot is immutable receipt metadata even when the release advances.

## Replay, unknown commit and capability lifetime

Completed same-key request first verifies current native/session/action and receipt disclosure authority for its exact patient/release/projection/purpose/AAL context. Obtain the authorized original metadata, prepare its exact versioned decryption capability outside locks, and (where artifactReview is present) verify original evidence under the disclosure contract outside locks. Final short transaction reauthorizes under current authority facts, validates original scope/hash/obligation/receipt links, decrypts locally, validates exact canonical bytes/generated response schema and immutable status/header/resource tuple, and returns ORIGINAL status/body/headers. No reconstruction from a newer head, new domain event or encryption. Missing old key/material, tag/context failure or lost current authority denies; no alternate snapshot/nonce/key fallback. Sensitive-read attribution remains the baseline; do not duplicate original mutation audit/outbox.

For commit-unknown, query the existing idempotency scope through current authorization before any new mutation/protection attempt. A visible completed record replays; a still-processing/locked competing transaction follows existing bounded in-progress behavior. A failed lookup/DB outage is unknown, not absence. Establish absence with a successful authoritative scope claim/lock after the prior transaction's outcome is settled; a claim encountering a committed winner discards preflight state and replays. Do not expire/delete a scope to infer absence of a possible committed clinical effect. Within the existing platform retention window, no blind second effect; no new retention duration/replay guarantee outside that platform contract is invented.

Crash before commit rolls back all five components. Known pre-commit rejection disposes capability/response buffers; a new attempt uses fresh receiptId/nonce, and fresh allergy revision/release domain envelope allocation where required. A concurrent loser MAY have performed preflight encryption before it learned of a winner; it commits no second effect. Committed replay performs no encryption. Key preparation is not re-encryption. No failed attempt reuses a GCM nonce with another plaintext.

Prepared capability is scoped to one attempt and permitted receipt encryption/decryption only, retained for the minimum transaction/disclosure interval. Prefer an opaque local capability with no export/log/serialization; if local key bytes are required, restrict buffer ownership and best-effort zeroize on commit/rollback/timeout/error, release handles and plaintext buffers in finally, never cache in global request state, dump or send keys to SQL. Managed-runtime copies cannot be promised perfectly zeroized; acceptance inspects ownership/disposal and forbidden sinks rather than claiming hardware erasure. No production KMS provider/lease behavior is assumed. If the configured provider cannot provide a bounded local capability, fail before mutation; network calls under locks are not an alternative.

## Acceptance owners and negatives

Contract preparation freezes envelope/columns/AAD/response serialization and independent neutral fixed bytes. Synthetic physical proof in BOTH runtimes validates deferred commit guard, same-connection finalization, tuple/FK/unique binding, immutable receipt/obligation, RLS/grants/non-owner roles, omission/wrong-finalizer/missing-audit/outbox rollback and no route exposure. Real producer composition proves schema-exact serialization, AES-GCM/random nonce/key/context/tag tamper, zero network/KMS/evidence calls under locks, capability disposal and all FIVE mutations with their exact canonical response including pre-resolved review material. Local serializer/crypto failure after domain work must roll back all components in both runtimes. Later application crash-before/after/commit-unknown/overlapping-loser/replay-authority-loss tests prove one effect and original bytes/status/headers after newer versions. No production/clinical gate is closed by these proofs.
